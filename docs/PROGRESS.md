## 识别层（2026-09-29 重做）

### 为什么换

老方案是「霍夫圆定位 → 逐格判占位 → 单样本模板匹配认兵种 → OCR 补字」。
实测下来两个致命问题：

1. **单样本模板匹配太脆**。每个兵种只有 1 张模板，且取自开局那一帧。棋子一旦被
   选中高亮（红圈光晕）、被走子动画覆盖、被落子提示白点挡住，形状就变了，匹配直接给错。
2. **以「认字」为核心路线本身就不对**。18px 的 车/卒、士/仕 本来就难分；
   开源界做同类事情的项目（TheOne1006）在 README 里明确写过「基于文字识别效果并不理想」。

实测证据（`out/snapshot_121645.png`，已逐格人工核对作真值）：

- 旧后端产出的 FEN 是 `rnbakabnr/.../RNBAKABNR`——**正好是标准开局**，
  把这一帧真实走过的两步棋（黑馬 (0,7)→(2,6)、红炮 (7,7)→(7,4)）抹平了。
  它不是"没认出来"，而是**按预期摆法猜了一个看着最合理的答案**。
- 旧后端在 `out/coach_125248.png` 上产出 22 子的残盘
  （`.../P1P1P3P/9/R8/2BAKA3`），这正是当初 `out/suggestion.json` 里
  送进引擎的那个 FEN——`validate_board` 判它「通过」，引擎照样出招。

### 换成了什么

**棋盘四点定位 → 透视拉正 → 整板一次性分类（10×9×16）**，这是开源界的共识做法。

- 棋盘四点不需要额外模型：`layout.json` 里已有 90 个交叉点，取四个角即可
  （左上/右上/左下/右下），少跑一个关键点模型就少一处出错点。
- 整板分类结构上保证 90 格全有输出，**从根上消灭"漏一个子整个局面就错"**。
- 模型来自 TheOne1006/chinese-chess-recognition 与 cheese2020/Chinese-Chess-Recognition
  共用的预训练权重（Apache-2.0），托管在 HuggingFace Space `yolo12138/Chinese_Chess_Recognition`。

### 预处理契约（**改了精度就掉，不要动**）

| 步骤 | 参数 |
|---|---|
| 透视拉正 | 棋盘四角 → 450×500 画布上 `padding=50` 的内框（即 (50,50)…(400,450)） |
| 中心裁剪 | 450×500 → 400×450（四边各切 25px，正好框住棋盘格区域） |
| 缩放 | → 280×315，正好 35px 一格 |
| 归一化 | RGB，mean `[123.675,116.28,103.53]`，std `[58.395,57.12,57.375]` |
| 张量 | NCHW float32，输入名 `input` |
| 输出 | `output` = `(batch, 90, 16)`，下标 `行*9+列`，16 类顺序见 `board_onnx.CLASSES` |

### 实测结果（`python tools/eval_recognition.py`）

| 方案 | 逐格准确率 | 子力召回 | 幻影 | 整盘全对 | 单帧耗时 |
|---|---|---|---|---|---|
| old 模板匹配 | 93.9% | 85.2% (52/61) | 2 | 0/2 | 114ms |
| new 整板 ONNX | **100%** | **100%** (61/61) | **0** | **2/2** | 628ms（含首次加载；热身后约 250ms） |

逐格准确率天然偏高（90 格里大部分是空位），**要看子力召回和整盘全对率**：
引擎要的是整盘正确，不是 98% 正确——错一个子就可能给出荒唐建议。

### 守门员（rules.py）

原来 `grid_classify.validate_board` 只查「子力数量上限 + 士象将位置」，所以那个
22 子残盘照样放行。新抽出的 `rules.py` 分两层：

- **静态**（单帧说得通）：将帅各一、子力不超编、士象将帅兵卒位置合法、
  **将帅不能照面**（这条能顺带抓出一批漏检）。
- **时序**（相邻帧说得通）：两帧差异必须能用 **≤3 步**合法着法解释（含吃子），
  或者回到标准开局；凭空多子/少子、一次动 4 处以上，才判 `noisy` 告警。

  为什么是"≤3 步"而不是"恰好 1 步"：管道确认一次盘面要好几秒，
  而正常对局里双方各走一步只要 2~3 秒——两次确认之间实际经常跨 2 步。
  旧版硬要求"恰好一步"，结果只要棋局在正常推进就**必然**误报，
  把正常对局一直说成「盘面与上一手对不上」。
  另外吃子必须单独处理：被吃的子会**同时**出现在两帧的差异里，
  不摘出来，连最普通的一步吃子都会被算成"一次动了 2 处"。

另外在**首次拿到稳定盘面时**严格比对标准开局（`rules.check_start`）。
这是唯一能拦住"自信的错答案"的时机——因为静态校验拦不住可达但错误的中局。
JJ象棋 有「棋力评测」等非标准开局模式，所以这里只告警不硬拦。

## 引擎强度与响应速度（2026-09-29 实测调优）

### 为什么"建议很蠢"——不是引擎笨，是参数把它饿死了

`start.ps1` 原来默认 `--depth 14`，而实测 pikafish 搜到深度 14 **只要 0.05 秒**，
等于瞟一眼就交卷。同一局面各档实测：

| 配置 | 耗时 | 到达深度 |
|---|---|---|
| `go depth 10` | 0.01s | 10 |
| `go depth 14` ← 旧默认 | **0.05s** | 14 |
| `go depth 18` | 0.44s | 18 |
| `go depth 20` | 1.05s | 20 |
| `go movetime 1000` | 1.00s | **23** |
| `go movetime 3000` | 3.00s | 24 |

注意 `depth 20` 花 1.05 秒才到 20 层，而 `movetime 1000` 花 1.00 秒到 23 层——
**别拿 depth 当强度旋钮**，它更像"最少搜多深"的下限；要棋力就用 movetime。

另外两处漏配：

- `Hash` 一直是引擎默认的 **16MB**（`coach.py` 只设了 Threads，漏了 Hash）。
  实测设 512MB + 8 线程后 nps **90 万 → 420 万**。
- `Threads` 硬编码 4，本机 16 核。

### 响应速度：瓶颈不在识别，在人为 sleep

单帧真实耗时 = 透视拉正 1.7ms + 预处理 2.3ms + **ONNX 推理 256ms**。
（`board_onnx.py --snapshot` 显示的 1.2~1.8s 是**每个新进程一次的模型加载**，
不是帧耗时——曾经被它误导过一次。）

旧版一轮 = `interval 1.5s` 纯 sleep + 推理 0.26s，还要连续 3 帧一致，
**确认一次盘面 5.4 秒**，而对局里对方一两秒就回招。现在改成两级：

1. 每轮只算一张整板缩略图（45×50，**0.9ms**）判断"画面变没变"，没变完全不碰 ONNX；
2. 画面确认稳定了才跑一次 ONNX 定案（256ms）。

阈值是标定出来的（拿 `out/` 里的历史快照两两比对）：同局面连续帧 `0.00000`、
只走掉一个子 `0.00578`、两个不同局面 `0.108~0.176` → 取 **0.002**。
另加兜底：画面若持续变化超过 `force_after`（默认 6s，落子高亮闪烁时会这样），
就不再等稳定、按当前帧强行定案，避免管道永远出不了结果。

### 着法历史（让引擎判得了重复局面）

`coach.py` 每次都用孤立 FEN 提问，引擎看不到之前下过什么，就判断不了重复局面
（三次重复算和棋）——该求和的盘当优势磨，能逼和的时候又看不出来。
现在 `app/auto_coach.py` 用 `MoveTrack` 维护「起点局面 + 着法序列」，
提问时发 `position fen <起点> moves <…>`。

安全性：每次追加着法都在本地重放一遍，只有重放结果与当前识别盘面**完全一致**
才接受；对不上（识别抖动）就地重置为当前局面。丢掉历史顶多少一个信息，
把错的历史喂给引擎才是真出事——引擎会基于一个不存在的局面给建议。

顺带修掉一个正确性问题：带历史后引擎能算出真实轮次，`moves` 个数为奇数
就意味着"我方刚落子、现在轮到对方"。旧版把 FEN 一律标成"我方走"，
这种时刻会给出基于**错误轮次**的建议；现在直接跳过并提示"轮对方走"。

### 运行期调参

`out/tune.json` 改了保存即生效，不用重启进程（引擎选项 `setoption` 本就支持热改）：

```json
{
  "movetime": 1000, "depth": null, "hash_mb": 512, "threads": null,
  "interval": 0.25, "stable": 2, "sig_thr": 0.002,
  "force_after": 6.0, "max_steps": 3
}
```

### 试过但**不要做**

- onnxruntime 调多线程：默认 256ms / 4 线程 270ms / 8 线程 305ms / 16 线程 325ms，
  **线程越多越慢**。
- 缩小网络输入分辨率：280×315 252ms、224×252 264ms、196×220 254ms，
  基本不省，还会破坏预处理契约。

## 目录调整与配置归位（2026-09-29）

根目录原来平铺着 20 来个文件，运行时代码、一次性脚本、文档、单页 HTML 混在一起。
按用途重分了目录：

- `app/` —— 运行时核心（`auto_coach` / `coach` / `rules` / `board_onnx` /
  `grid_classify` / `hud`）。这 6 个模块之间是"同目录裸 import"（`import rules` 这种），
  放进同一个目录后 **import 一行都不用改**。
- `tools/` —— 辅助与一次性脚本（标定、探测、评测、下载、早期实现）。
- `docs/` —— 文档与那个单页 HTML（`docs/index.html`）。

**配套改动（不做这些就会到处找不到文件）**：所有以"脚本所在目录"为基准的路径
（`os.path.join(HERE, "config"…)`）都改成**以项目根为基准**
（`ROOT = os.path.dirname(HERE)`）——脚本现在下沉了一层。
`tests/` 通过 `sys.path.insert(0, ROOT/"app")` 找到运行时模块。

另外把 `tune.json` 从 `out/` 挪到了 `config/`：`out/` 整个目录是运行期产物、
被 `.gitignore` 挡着，配置放里面换台机器就丢了。启动时会自动把老位置的
`tune.json` 迁移过来并删除老文件（一次性）。

## 坐标与验证（已写入 config/layout.json）

- 窗口（标定时）：`rect=(8,413) 326x606`
- 棋盘格：9 列 × 10 行，**正方形格**，格距 `34.0 px`
- 左上角 `(21.5, 167.5)`，右下角 `(293.5, 473.5)`
- 90 个交叉点坐标已全量写入配置

两条**互相独立**的证据证明这组坐标可信（不是猜的）：

1. **几何**：32/33 个棋子圆心落在拟合网格交点上——象棋开局正好 32 个子
2. **文字**：OCR 读到的 `楚河` `汉界` 落在第 4–5 行之间，`車馬象士将士象馬車` 落在第 0 行

- 中间失效过一次：按圆心直接聚类得到的行/列间距是 `34.0 vs 51.1`（明显不等），
  说明聚类**漏了整行车**；改成强制正方形网格拟合后修复。
- **遗留**：网格仍是一次性标定写死，没有逐帧复核。实测格点与真实棋子圆心有
  dx +2~+7px、dy −1.4~−3.7px 的系统偏差。整板分类对这个量级的偏差不敏感
  （拉正后每格 35px），但若窗口缩放变化较大仍会退化——后续可加逐帧网格重估。
