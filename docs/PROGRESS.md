## 识别层（2026-09-29 重做）

### 为什么换

老方案是「霍夫圆定位 → 逐格判占位 → 单样本模板匹配认兵种 → OCR 补字」。
实测下来两个致命问题：

1. **单样本模板匹配太脆**。每个兵种只有 1 张模板，且取自开局那一帧。棋子一旦被
   选中高亮（红圈光晕）、被走子动画覆盖、被落子提示白点挡住，形状就变了，匹配直接给错。
2. **以「认字」为核心路线本身就不对**。18px 的 车/卒、士/仕 本来就难分；
   开源界做同类事情的项目（TheOne1006）在 README 里明确写过「基于文字识别效果并不理想」。

实测证据（`out/snapshot_121645.png`，已逐格人工核对作真值）：

- 旧后端产出的 FEN 是 `rnbakabnr/.../RNBAKABNR`——**正好是标准开局**，
  把这一帧真实走过的两步棋（黑馬 (0,7)→(2,6)、红炮 (7,7)→(7,4)）抹平了。
  它不是"没认出来"，而是**按预期摆法猜了一个看着最合理的答案**。
- 旧后端在 `out/coach_125248.png` 上产出 22 子的残盘
  （`.../P1P1P3P/9/R8/2BAKA3`），这正是当初 `out/suggestion.json` 里
  送进引擎的那个 FEN——`validate_board` 判它「通过」，引擎照样出招。

### 换成了什么

**棋盘四点定位 → 透视拉正 → 整板一次性分类（10×9×16）**，这是开源界的共识做法。

- 棋盘四点不需要额外模型：`layout.json` 里已有 90 个交叉点，取四个角即可
  （左上/右上/左下/右下），少跑一个关键点模型就少一处出错点。
- 整板分类结构上保证 90 格全有输出，**从根上消灭"漏一个子整个局面就错"**。
- 模型来自 TheOne1006/chinese-chess-recognition 与 cheese2020/Chinese-Chess-Recognition
  共用的预训练权重（Apache-2.0），托管在 HuggingFace Space `yolo12138/Chinese_Chess_Recognition`。

### 预处理契约（**改了精度就掉，不要动**）

| 步骤 | 参数 |
|---|---|
| 透视拉正 | 棋盘四角 → 450×500 画布上 `padding=50` 的内框（即 (50,50)…(400,450)） |
| 中心裁剪 | 450×500 → 400×450（四边各切 25px，正好框住棋盘格区域） |
| 缩放 | → 280×315，正好 35px 一格 |
| 归一化 | RGB，mean `[123.675,116.28,103.53]`，std `[58.395,57.12,57.375]` |
| 张量 | NCHW float32，输入名 `input` |
| 输出 | `output` = `(batch, 90, 16)`，下标 `行*9+列`，16 类顺序见 `board_onnx.CLASSES` |

### 实测结果（`python tools/eval_recognition.py`）

| 方案 | 逐格准确率 | 子力召回 | 幻影 | 整盘全对 | 单帧耗时 |
|---|---|---|---|---|---|
| old 模板匹配 | 93.9% | 85.2% (52/61) | 2 | 0/2 | 114ms |
| new 整板 ONNX | **100%** | **100%** (61/61) | **0** | **2/2** | 628ms（含首次加载；热身后约 250ms） |

逐格准确率天然偏高（90 格里大部分是空位），**要看子力召回和整盘全对率**：
引擎要的是整盘正确，不是 98% 正确——错一个子就可能给出荒唐建议。

### 守门员（rules.py）

原来 `grid_classify.validate_board` 只查「子力数量上限 + 士象将位置」，所以那个
22 子残盘照样放行。新抽出的 `rules.py` 分两层：

- **静态**（单帧说得通）：将帅各一、子力不超编、士象将帅兵卒位置合法、
  **将帅不能照面**（这条能顺带抓出一批漏检）。
- **时序**（相邻帧说得通）：两帧差异必须能用 **≤3 步**合法着法解释（含吃子），
  或者回到标准开局；凭空多子/少子、一次动 4 处以上，才判 `noisy` 告警。

  为什么是"≤3 步"而不是"恰好 1 步"：管道确认一次盘面要好几秒，
  而正常对局里双方各走一步只要 2~3 秒——两次确认之间实际经常跨 2 步。
  旧版硬要求"恰好一步"，结果只要棋局在正常推进就**必然**误报，
  把正常对局一直说成「盘面与上一手对不上」。
  另外吃子必须单独处理：被吃的子会**同时**出现在两帧的差异里，
  不摘出来，连最普通的一步吃子都会被算成"一次动了 2 处"。

另外在**首次拿到稳定盘面时**严格比对标准开局（`rules.check_start`）。
这是唯一能拦住"自信的错答案"的时机——因为静态校验拦不住可达但错误的中局。
JJ象棋 有「棋力评测」等非标准开局模式，所以这里只告警不硬拦。

## 引擎强度与响应速度（2026-09-29 实测调优）

### 为什么"建议很蠢"——不是引擎笨，是参数把它饿死了

`start.ps1` 原来默认 `--depth 14`，而实测 pikafish 搜到深度 14 **只要 0.05 秒**，
等于瞟一眼就交卷。同一局面各档实测：

| 配置 | 耗时 | 到达深度 |
|---|---|---|
| `go depth 10` | 0.01s | 10 |
| `go depth 14` ← 旧默认 | **0.05s** | 14 |
| `go depth 18` | 0.44s | 18 |
| `go depth 20` | 1.05s | 20 |
| `go movetime 1000` | 1.00s | **23** |
| `go movetime 3000` | 3.00s | 24 |

注意 `depth 20` 花 1.05 秒才到 20 层，而 `movetime 1000` 花 1.00 秒到 23 层——
**别拿 depth 当强度旋钮**，它更像"最少搜多深"的下限；要棋力就用 movetime。

另外两处漏配：

- `Hash` 一直是引擎默认的 **16MB**（`coach.py` 只设了 Threads，漏了 Hash）。
  实测设 512MB + 8 线程后 nps **90 万 → 420 万**。
- `Threads` 硬编码 4，本机 16 核。

### 响应速度：瓶颈不在识别，在人为 sleep

单帧真实耗时 = 透视拉正 1.7ms + 预处理 2.3ms + **ONNX 推理 256ms**。
（`board_onnx.py --snapshot` 显示的 1.2~1.8s 是**每个新进程一次的模型加载**，
不是帧耗时——曾经被它误导过一次。）

旧版一轮 = `interval 1.5s` 纯 sleep + 推理 0.26s，还要连续 3 帧一致，
**确认一次盘面 5.4 秒**，而对局里对方一两秒就回招。现在改成两级：

1. 每轮只算一张整板缩略图（45×50，**0.9ms**）判断"画面变没变"，没变完全不碰 ONNX；
2. 画面确认稳定了才跑一次 ONNX 定案（256ms）。

阈值是标定出来的（拿 `out/` 里的历史快照两两比对）：同局面连续帧 `0.00000`、
只走掉一个子 `0.00578`、两个不同局面 `0.108~0.176` → 取 **0.002**。
另加兜底：画面若持续变化超过 `force_after`（默认 6s，落子高亮闪烁时会这样），
就不再等稳定、按当前帧强行定案，避免管道永远出不了结果。

### 着法历史（让引擎判得了重复局面）

`coach.py` 每次都用孤立 FEN 提问，引擎看不到之前下过什么，就判断不了重复局面
（三次重复算和棋）——该求和的盘当优势磨，能逼和的时候又看不出来。
现在 `app/auto_coach.py` 用 `MoveTrack` 维护「起点局面 + 着法序列」，
提问时发 `position fen <起点> moves <…>`。

安全性：每次追加着法都在本地重放一遍，只有重放结果与当前识别盘面**完全一致**
才接受；对不上（识别抖动）就地重置为当前局面。丢掉历史顶多少一个信息，
把错的历史喂给引擎才是真出事——引擎会基于一个不存在的局面给建议。

顺带修掉一个正确性问题：带历史后引擎能算出真实轮次，`moves` 个数为奇数
就意味着"我方刚落子、现在轮到对方"。旧版把 FEN 一律标成"我方走"，
这种时刻会给出基于**错误轮次**的建议；现在直接跳过并提示"轮对方走"。

### 运行期调参

`config/tune.json` 改了保存即生效，不用重启进程（引擎选项 `setoption` 本就支持热改）：

```json
{
  "movetime": 3000, "depth": null, "hash_mb": 1024, "threads": null,
  "interval": 0.25, "stable": 2, "sig_thr": 0.002,
  "force_after": 6.0, "max_steps": 3
}
```

### 默认值按实机二次标定

机型 i7-11700（8 核 16 线程）/ 32GB 内存。中局局面，每轮前清空哈希：

- **思考时间**：1000ms → 深度 18、2000 → 21、**3000 → 22**、5000 → 25。
  默认据此从 1000ms 提到 **3000ms**。
- **线程数**：2/4/6/8/12/16 的到达深度都在 19~21，而 nps 从 79 万涨到 348 万
  ——**多线程并没有转化成深度**。保持自动（`cpu_count//2`，上限 8）即可，
  别把核占满。
- **Hash**：128MB → 19、512MB → 21、1024/2048 与 512 持平。512MB 就饱和了，
  默认取 1024MB 只是给长对局留余量。

### 复核：movetime 其实是「上限」（6 局面 × 4 档 A/B，2026-09-29）

有人把 `tune.json` 手工改成了 `movetime 10000`，担心"想久一点是不是更准"。做了 A/B
（脚本 `out/tune_ab.py`，Threads 8 / Hash 1024，同机 i7-11700）：

| 局面 | 1000ms | 2000ms | 3000ms | 10000ms |
|---|---|---|---|---|
| 开局 | c3c4 d20 | c3c4 d21 | h2e2 d23 | h2e2 d28 |
| 2步 | h0g2 d20 | h0g2 d23 | g3g4 d23 | h0g2 d29 |
| 6步 | g3g4 | g3g4 | g3g4 | g3g4 |
| 12步 | a0a1 | a0a1 | a0a1 | a0a1 |
| 对弈中局（自我对弈 20 步） | g3g4 d20 | g3g4 d24 | g3g4 d26 | g3g4 d34 |
| 车单残局 | e1f1 mate1 **5ms** | 同 | 同 | 同 |

- 24 个组合 19 个一致，5 个不一致**全部**在"开局/2步"这两个均势多解局面，
  评分差 1~6 cp = 等价着法互换。**中局、残局 100% 一致。**
- 残局认出 `mate 1` 只花 **5~9ms** 就返回 —— `movetime` 是上限不是固定耗时。
- **pikafish 没有开局库**（UCI 选项无 `BookFile`），开局纯搜索，几 cp 内摇摆属正常。
- 注意单局面不能外推：早先只拿"6 步"一个局面测，三档全同，看着像"时间完全无用"，
  其实是因为那个局面已经收敛。

处置：`tune.json` 回到 `movetime 3000`、`interval 0.25`。同一局面的端到端延迟
从约 11 秒降到约 3.8 秒，而中局/残局棋力不变。

### 异步搜索与进程优先级（2026-09-29）

#### 为什么

原来主循环是一条线走下来的：等画面稳定 → 识别 → 问引擎。`eng.bestmove()`
把这条线**堵在引擎那儿**——搜索的这几秒里它既不抓图也不看画面。对手要是在
这几秒里落了子，得等搜索跑完才发现局面变了，那几秒纯属白搜。快棋
（双方 2~3 秒一步）下这段能有 1~2.5 秒；反过来，如果你每步想得久，收益≈0。
（注意它省的不是识别时间：搜索必须等识别出局面才能开始，两者不是并行的。）

#### 改了什么

- `coach.Engine` 拆出异步三件套：`start()` 发起、`step()` 推进（**timeout=0
  是非阻塞轮询**，拿到 bestmove 立刻返回、不凑满超时）、`take()` 取结果，
  外加 `expired()` 兜底。`bestmove()` 保留，内部就是"start → 循环 step → take"，
  行为与重构前**逐字一致**（`test_engine_recover.py` 一字没改仍然全过）。
- 主循环引入 `pending`：搜索期间每轮照常抓图，画面一变就 `resync()` 取消、
  重新识别；搜索跑完才出建议。
- `pending` 里存着出建议所需的**全部上下文**（board / 子力数 / warn / 历史步数 /
  完整 FEN）。等到结果的那一轮盘面可能已经翻篇，那时再去读当前循环的
  `board` / `track` 就张冠李戴了——这正是异步最反直觉的地方。
- `pending` 分支必须放在**稳定判定之前**。画面没变时下面那个"已经定过案"的
  分支会直接 `continue`，搜索就永远推进不到头。
- 失败恢复抽成 `recover_engine()`：拒收局面 / 进程没了 → 重启；超时 → 拉平
  管道（否则它稍后吐出的 bestmove 会被下一问当成新局面的答案）；无着可走 →
  什么都不做。`ask_engine()`（同步 + 立刻重问一次）保留，给测试和一个
  "问一次就拿结果"的场景用。
- `eng.start()` 的返回值必须检查：命令没送进引擎时不能挂成 pending，否则要
  白等 20 秒兜底超时才有人收拾，这一手还出不来。

#### 进程优先级

- `coach.set_process_priority()` 提本进程（识别跑在这儿）；
  `Engine.spawn()` 用 `creationflags=ABOVE_NORMAL_PRIORITY_CLASS` 提引擎子进程。
- **踩到的坑**：`set_process_priority` 必须显式声明 `argtypes` / `restype`。
  ctypes 默认把返回值当 `c_int`，而 `GetCurrentProcess()` 返回的伪句柄是 -1
  （64 位下 0xFFFF…FFFF），截成 32 位后 `SetPriorityClass` 拿到无效句柄、
  **静默失败返回 0**——代码看着毫无问题，只是"没生效"。第一版就栽在这儿，
  日志里明明白白写着"优先级没提上去"。
- 不用 `HIGH` / `REALTIME`：那会拖累整机响应，`ABOVE_NORMAL` 只是略高。

#### 验证

- `tests/test_engine_async.py`（新增，13 条）：三件套与同步 `bestmove()` 等价、
  `step(0)` 确实不阻塞、**取消后残留输出不漏到下一问**（异步路径上最危险的地方，
  串了就会给出属于上一个局面的着法，而用户在界面上看不出来）、异步下的失联
  判定与恢复、两级优先级真的落地（子进程与本进程都是 0x8000）。
- `tests/run_all.py` 6 个文件全过。
- 真机冒烟：启动 12 秒，日志出现「进程优先级已提到 AboveNormal」，
  退出后无残留 pikafish 进程。

### 试过但**不要做**

- onnxruntime 调多线程：默认 256ms / 4 线程 270ms / 8 线程 305ms / 16 线程 325ms，
  **线程越多越慢**。
- 缩小网络输入分辨率：280×315 252ms、224×252 264ms、196×220 254ms，
  基本不省，还会破坏预处理契约。

## 目录调整与配置归位（2026-09-29）

根目录原来平铺着 20 来个文件，运行时代码、一次性脚本、文档、单页 HTML 混在一起。
按用途重分了目录：

- `app/` —— 运行时核心（`auto_coach` / `coach` / `rules` / `board_onnx` /
  `grid_classify` / `hud`）。这 6 个模块之间是"同目录裸 import"（`import rules` 这种），
  放进同一个目录后 **import 一行都不用改**。
- `tools/` —— 辅助与一次性脚本（标定、探测、评测、下载、早期实现）。
- `docs/` —— 文档与那个单页 HTML（`docs/index.html`）。

**配套改动（不做这些就会到处找不到文件）**：所有以"脚本所在目录"为基准的路径
（`os.path.join(HERE, "config"…)`）都改成**以项目根为基准**
（`ROOT = os.path.dirname(HERE)`）——脚本现在下沉了一层。
`tests/` 通过 `sys.path.insert(0, ROOT/"app")` 找到运行时模块。

## 引擎失联与日志（2026-09-29）

### 起因：界面上一句「引擎没给着法（局面可能不合法）」糊住了四种故障

实测这四种的性质完全不同，处理方式也不一样：

| 情况 | 引擎的表现 | 重试有用吗 |
|---|---|---|
| 无着可走（绝杀 / 困毙） | 回 `bestmove (none)`，进程**正常活着** | 没用，重问一百次还是 `(none)` |
| 引擎拒收局面 | 打印 `info string CRITICAL ERROR: ... Reason: Unsupported position. King can be captured.` 后**自己退出** | 没用（等于再打死一次）；但**必须重启进程** |
| 提问超时 | 还活着，只是没在预算内回话 | 有用，但要先拉平管道 |
| 进程崩了 / 管道断了 | 读操作立刻拿到 EOF | 有用（重启） |

实测原始数据（把引擎单独拉起来问）：

- **不合法局面**（`4k4/9/9/9/9/9/9/9/9/4K4 w`，将帅照面）：
  引擎吐一行 `CRITICAL ERROR ... King can be captured` 之后进程就没了，
  `poll()` 非空、`readline()` 立刻空串——客户端把它当成 `bestmove=None`，
  于是界面显示"没给着法"。此后再往它的 stdin 写一句，
  立刻 `OSError: [Errno 22] Invalid argument`。
- **无着可走**（黑方被绝杀、轮黑走）：`info depth 0 score mate 0` + `bestmove (none)`，
  进程活着。老代码只判 `if not mv`，把"我确实没招"和"我不理你"混成一件事。
- **关键结论**：引擎拒收局面之后管道就永久废了。老代码不重启进程，
  于是后面每一次提问都失败；日志当时还不存在，只留下重复的同一句话，根因被埋掉。

### 改了什么

1. `coach.Engine` 换成**读线程 + 队列**，所有等待都带真实超时。原来是直接
   `readline`——引擎一不吭声就把进程按死在那儿，那句"预算超时"的判断
   只在两行之间才轮得到执行，等于没有。
2. `bestmove()` 一定写下 `self.reason`（`no_legal_move` / `invalid_position` /
   `dead` / `timeout` / `empty_bestmove`），并把引擎吐的 `info string` 收进
   `self.diag`（它拒收局面的原因就在那里）。`send()` 改成返回布尔值，
   往已经死掉的进程写不再抛异常——"引擎死了"是可恢复的，不该拖垮整条管道。
3. 新增 `resync()`（发 `stop`，然后读到 `readyok` 为止把中间输出全丢掉）和
   `restart()`。前者防的是**错位配对**：超时之后引擎其实还在搜，它稍后吐出的
   bestmove 会被下一次提问当成新局面的答案——那比不给答案更糟，会照着错的建议走棋。
4. `auto_coach.ask_engine()` 按原因决定动作：只有 `dead` / `timeout` 才重问
   （一次），`invalid_position` 不重问但当场重启进程，`no_legal_move` 直接认账。
5. 守门员加一条 `rules.king_capturable()`：轮到我走、而我方已经能吃对方的将
   → 这个局面不喂给引擎。合法对局里它不可能出现（对方被将军就必然轮到对方走），
   真出现就说明轮次或识别错了——差分异常后重置着法历史正好会这样。
   它的判据和引擎是同一个，所以拦它不会误杀引擎本来愿意接受的局面。
6. 日志落到根目录 `log/`（已加入 `.gitignore`）。记的是"事后真查得动"的东西：
   完整 FEN、校验没过的**全部**问题、差分异常的两帧 FEN、
   引擎的下发命令 / 原始输出 / 退出码 / 重启记录。

## 轮次：从写死「我方」改成真实状态（2026-09-29 修引擎拒收局面）

### 症状

`log/engine-*.log` 里规律性出现

```
info string CRITICAL ERROR: ... Reason: Illegal move: h7f7
```

之后 pikafish **自己退出**，`auto_coach` 只好重启进程，这一手的建议就丢了。
15:04 / 15:07 / 15:08 各一次，`moves` 分别是 `h7f7 b0c2`、`f7f2 a0b0`、
`e2e1 f2b2 h9g7 b0b2`——共同点是**第一手不归"起点 FEN 说的那一方"**。

### 根因：着法的先后顺序没人管轮次

1. `rules.move_legal()` 只判几何形状（子系统/路径/蹩腿），不看轮到谁走。
2. `explain_change()` 原来**只重排"目的地"、不重排"谁先谁后"**，而先后直接等于
   `movers` 的行优先顺序。两步互不相干（不互吃、路径不冲突）时正反两种顺序在
   几何上都成立，于是黑方那一步（行号小、靠上）**永远**被排到第一手。
3. `board_to_fen(board, args.side)` 把每个 FEN 一律标成"我方走"，
   引擎据此要求第一手归我方 → 直接判 illegal。
4. `MoveTrack.push()` 也只调 `move_legal`，没有轮次概念，错序历史被原样收下并累积
   （那条 4 步历史就是这么攒的：前两步被几何唯一确定所以顺序对了，后两步排反了）。

### 改法

- `explain_change(prev, cur, max_steps, first_side=None)`：**配对和先后都穷举**
  （≤3 步最多 3!×3! = 36 种），只接受"首手归 `first_side`、之后逐手交替"的排列；
  一条都排不出来就返回 `noisy`，由上层决定是纠正轮次还是丢掉历史。
  不给 `first_side` 时第一个解就是原来的遍历顺序，行为与旧版逐字一致。
- `MoveTrack` 现在持有**轮次**（`turn` + `start_pos`），起点 FEN 由
  `(start_pos, turn)` 现算——FEN 标注和历史首手从此同源，不可能矛盾。
  `push()` 逐步校验"这一步归谁走"，`history_turn_ok()` 是提问前的最后一道保险
  （真出问题也只是丢历史退化成孤立局面，不会再让引擎自杀一次）。
- **中途进场**的轮次从哪来：`--turn red|black|auto`（默认 auto）→
  `rules.guess_turn()` 从局面推断（`king_capturable` 双向用：我方能吃到对方的将
  就不可能轮我方；对方能吃到我方的将就轮我方）→ 都判不出就按我方算并**告警**。
- 猜错了能自纠：差分解释不通时换个轮次再试一次，成立就翻过来重排。
- 删掉 `len(moves) % 2` 那个奇偶判断，直接看 `track.expect_first()`。
- 守门员没过的那一帧**不再跑差分**（过去会跑，等于让说不通的盘面去改着法历史）。

### 验证

- `tests/run_all.py` 4 个文件全过：`test_rules_diff.py` 新增 5 条顺序断言，
  `test_tune_track.py` 新增 13 条（轮次拒绝、历史自检、中途进场推断）。
- 临时脚手架（在 `out/` 下，不入库）：`repro_history_order.py` 用日志里那两帧复现，
  修前退出码 1、修后 PASS；`smoke_midgame.py` 模拟中途进场 + 轮次自纠，产出的
  `position fen … b - - 0 1 moves h9g7` 丢给真 pikafish 正常出 `bestmove`。
- 真引擎对照：`moves h7f7 b0c2` → `CRITICAL ERROR: Illegal move` 后退出；
  `moves b0c2 h7f7` → 正常出招。

### 顺带修的

- `coach.board_to_fen()` 现在也收纯标签（着法历史里存的就是标签，没有分数）。
- `coach.rc_to_ucci()` 的 docstring 写 `(9,0) -> 'a9'` 是错的，实际是 `'a0'`。
- `kind == "same"` 不再落进"差分异常"分支——识别连续不确定后放手重来会重新确认
  同一帧，日志里刷"差分异常（）"是误报。

## 重置开关与子力骤降基线（2026-09-29 修「一局下完就再也不出招」）

### 现场

用户反馈「助手只能开一局」。翻 `log/auto_coach-2026-09-29.log` 复现得很清楚：

| 时间 | 事件 |
|---|---|
| 16:03:37 → 16:05:34 | 正常出招：炮八平五、马二进三…一路到「前车六进一」 |
| 16:06:27 | 首次 `识别不确定：子力 42 -> 29 骤降，疑似漏检` |
| 16:06:38 → 16:11:24 | **全是 `子力 42 -> N 骤降`，之后再没出过任何一手** |

### 根因：基线被坏帧污染，然后自我固化

守门员里那条「一步最多吃掉一个子，子力不该骤降」，基线 `last_count`
过去是在**校验之前**就被改写的：

```python
n_now = len(occ)
if last_count is not None:
    if n_now > last_count + 2:
        last_count = n_now          # ← 坏帧在这里就把基线改掉了
    elif last_count - n_now > 2:
        problems.append("子力 {} -> {} 骤降".format(last_count, n_now))
if problems:
    ok = False
```

那句 `last_count = n_now` 的本意是"子力变多当作新开一局"（新局 20 子 → 32 子
不该误报）。但**坏帧恰恰就是子力暴涨的形态**：识别崩掉时会读出 42 子（棋盘上限 32）。
基线一变成 42，之后每一帧正常盘面（32、29、24…）全被判「42 -> N 骤降」，
守门员永久不放行——**助手连一局都跑不完**。

旧的"放手重来"也没救回来：`bad_n >= 3` 时只清了 `last_key`，没清 `last_count`，
所以它自己也走不出这个循环。

### 修法

- 骤降判定抽成纯函数 `auto_coach.power_drop()`，**只判降不判升**。子力变多只可能是
  新开一局，或者识别把空位认成了子——前者无害，后者由静态校验的子力上限兜住。
  判定里绝不动基线。
- `last_count` 只在**守门员通过之后**更新（`last_count = len(occ)`），坏帧再也改不动它。
  顺带把 `bad_n >= 3` 的"放手"也补上清 `last_count`——识别崩过一阵又恢复时，
  恢复后的第一帧不会继续被旧基线判死。

### 新增：手工「重开一局」

修好基线之后，第二件事是**给一个不看盘面、直接清空状态的入口**。原来"开新局"
只有一条自动路径：盘面回到标准 32 子开局时 `rules.explain_change` 返回 `reset`。
可 JJ象棋 有「棋力评测」这类非标准开局模式，认不出 `reset`，于是轮次一直继承
上一局（15:57、16:03 两次启动的症状就是卡在"轮对方走"）。

- 浮窗加「重开一局」按钮 → 写 `out/restart.flag`（跨进程只能靠文件，
  `suggestion.json` 也是这么传的）。
- `auto_coach.restart_requested()` 读到就**把文件删掉**（一次性信号），然后清空
  `track / last_board / last_key / last_count / last_move / bad_n / sig_done / still_n`，
  让下一帧走"首帧"那套：重新按 `--turn` → 局面推断 → 我方 定轮次，不再继承上一局。
- `sig_prev` 有意**不清**：留着它，画面没变时下一轮不会走进"画面变化中…"，
  「已重置」这句状态才能在浮窗上多停一会儿。
- 浮窗没开时兜底：`New-Item out\restart.flag -ItemType File -Force`。

### 验证

- `tests/test_restart.py`（新增，16 条）：`power_drop` 的容差边界、"子力变多不报"，
  以及"基线被污染后会持续误报"——这条钉住的是"修复点在主循环而不在判定里"；
  `restart_requested` 的一次性消费语义与"目录不存在也不炸"。
- `tests/run_all.py` 5 个文件全过。

### 为什么「重开一局」看着没用

开关本身没问题：16:35:37 点按钮，16:35:37.938（0.1 秒后）就出了新的识别结果，
日志也确认信号被消费。但重开只清「着法历史 / 轮次 / 子力基线」，**不修正朝向**，
所以清完读到的还是同一张翻转的盘面，守门员照样拦。

### 修法

改动全在 `board_onnx.py`（当时 `auto_coach.py` / `coach.py` 正被另一处改动占着，避开）：

- `looks_flipped(board)`：判据优先用象棋硬约束——**帅必在 row 7~9、将必在
  row 0~2**（九宫），比按子力重心猜稳得多；将帅都没认出来时才退回重心比较。
- `flip_rows(board)`：`r -> 9-r` 镜像；`_FLIP_ORDER` 把 `prob` 一起重排，两者不脱节。
- `classify()` 在 `flip=None` 时自动判断并镜像，**不重跑推理**——模型认的是每格
  棋子的外观，反的只是行号的语义。
- 兜底：`layout.json` 写 `board.flip: true/false` 可钉死朝向；`board_onnx.py`
  命令行加了 `--flip auto|yes|no`。
- 翻过去的那一刻提示一次（`_note_flip`，不刷屏），会落到 `log/coach.out.log`。

### 验证

- `tests/test_board_flip.py`（新增，21 条）：标准开局与其镜像、将帅硬约束
  （单看红帅在 row 0 / 黑将跑到 row 9）、退重心、认不全时保守不翻转、
  镜像对合性，以及与 `rules.validate` 串起来的两个方向。
- 实机抓图：翻转的开局经校正后输出 `B車 ‥ B象 B士 B將 … / R車 R相 R仕 R帥 …`，
  朝向正确。

## 着法历史被引擎拒收 / 截断（2026-09-29 修）

### 现场

用户问"为什么给的走棋步骤里有 `h0h7` 这种"。查下来不只是显示格式问题。

`coach.move_to_chinese()` 在**起点格读不到棋子**时直接原样返回 UCCI 坐标：

```python
if lab == "EMPTY":
    return mv
```

所以 `h0h7`（中文是"车二进七"）露出来，说明**引擎给的这手棋，起点在当前识别出的
盘面上是空的**——即引擎看的局面和这一帧不是同一个。

### 实测

1. 把日志里记的 FEN 原样拿去问引擎，引擎给的着法**不是日志记的那个**，而是另一个
   "起点有子的"着法——同一张 FEN，两套结果。
2. 三条"露出 UCCI"的记录，起点**全是棋子的原始位置**：`h0h7`→(9,7) 红车、
   `d0e1`→(9,3) 红仕、`a0a1`→(9,0) 红车。引擎实际停在**很早的局面**上。
3. 探针（monkey patch `Engine.start`，不改文件）看到：`start_fen` 一直是**首帧那个
   18 子的局面**，而 `moves` 已经累积到 4 步——说明引擎并没有按"起点 + 4 步"走。

### 根因

`position fen <起点> moves <…>` 里，pikafish 是用它的 `pos.legal` 逐步校验的，而
`rules.move_legal` 的注释自己就写着"**只做必要的形状检查，不查将军/自将**"。
两者不等价，于是差分推出来的着法链可能被引擎拒收。实测那会让引擎：

```
info string CRITICAL ERROR: Command `position fen … moves h0h7` failed.
                          Reason: Illegal move: h0h7
```

然后**自己退出**（`reason=invalid_position`、`alive=False`）。就算这一手没被判非法，
只要历史里某一步不合法，后面的着法会被**静默跳过**，引擎就停在很早的局面上——
它给出的着法起点自然和当前帧对不上。

### 修法

- `auto_coach.MoveTrack.push()` 每走一步后补一次
  `rules.king_capturable(work, 对方)`——走完不能让自己的将处于被吃状态，这正是引擎
  `pos.legal` 会查的。代价是 ≤3 步 × 一次子力遍历，可忽略。
- `coach.move_to_chinese()` 起点读不到棋子时返回 `？（h0h7）` 而不是原样吐坐标——
  `h0h7` 看着像正常建议，实际根本对不上棋盘，照着走就是走错棋。
- `auto_coach.ask_engine()` 把引擎拒收时的 `diag` 原文记进主日志（含它抱怨的那条
  命令），下次一眼能看到是**哪一步**不合法。

### 验证

- `tests/test_tune_track.py` 新增 6 条：送将的着法被拒、正常着法不被误杀、
  起点没子时记谱明确标注。
- `tests/run_all.py` 7 个文件全过。

### 还没钉死的

`start_fen + moves` 与当前帧之间到底在哪一环脱节，只定位到"引擎没有按整条历史走"。
再往下要复现就需要窗口在对局中，本轮没凑齐（探针跑到时 JJ象棋 窗口已隐藏）。
不过上面三处改动已经把两条失效路径都堵住了：历史被拒收（补了 legal 校验）、
以及即使脱节也不会再把坐标伪装成正常建议。

## 轮次待定：判不出轮次时先不出招（2026-09-29 修「对方先手就多走一步」）

### 问题

"对方先手"时助手给出的着法**时机是错的**。用户问的是"对方先手你是不是就不会走了"，
实测恰恰相反——它走得太早。把主循环里"守门员过 → 差分 → 判轮次 → 出不出招"那段抽成
`out/sim_turn.py`（逐帧对照"实际该谁走"的奇偶真值）跑出来的形态：

| 进场时机 | 改动前 |
|---|---|
| 执黑 + 标准开局 | 首帧就按"黑方走"算，给出黑方第一手——而实际还没轮到黑方 |
| 中途进场 + 正轮到对方 | 首帧给出我方的着法（对方那手还没发生）→ 照着走等于多走一步 |
| 中途进场 + 正轮到我方 | 猜对了，正常出招 |

根因是 `resolve_turn()` 猜不出轮次时**一律回退「我方走」**。`rules.guess_turn()` 只能靠
"谁能吃到对方的将"判断，平静局面（尤其开局）根本判不出来，于是这条回退在"我方先手"
时天然成立、在"对方先手"时必然错。

自纠仍然存在（差分解释不通就换一种轮次重排），代价是 track 从 `last_board` 重建、
**着法历史整段丢弃**——日志里反复的「起始轮次判错了」就是这么来的，历史长期只有 1~2 步。

### 改法

1. **标准开局不再算"猜"**：`resolve_turn` 里加一条 `pos == rules.SETUP` → 必然红先。
   32 子全在原位只有一种可能，这是**推出来的**。于是执黑开局从"必然猜错"变成完全正确，
   执红开局照旧首帧就出招（没有退化）。
2. **推不出来就先不出招**：`MoveTrack` 新增 `turn_confirmed`（默认 True）。首帧判不出时
   置 False，主循环在"轮对方走"那条门**之前**先拦：`if not track.turn_confirmed:
   浮窗写 TURN_PENDING_TEXT; continue`。顺序不能反——反了浮窗显示的是"轮对方走"，
   而那正是我们不知道的事。
3. **等一手落子由差分反推**：`MoveTrack.adopt(seq, base)` 只接受**恰好一手**
   （`len(seq) == 1`，且 base 与自己持有的局面一致），把轮次定成"走这一手的那一方"。
   为什么拒绝多步：一次动两处时先后顺序本身就是不确定的（见上面 `explain_change`
   那段"顺序也得枚举"），顺序一错推出来的轮次就跟着错——那正是要躲开的东西。
4. 轮次待定期间不拿它当差分约束（`first_side=None`）；差分解释不通时也只是把基准挪到
   当前帧继续等，**不顺手按"我方走"认下来**。
5. `--turn red|black` 仍是硬指定（直接 confirmed），给不想等这一手的人用。

### 代价（明说）

轮次认不出 **且其实该我走** 时，进场后要等一手才有建议（`sim_turn.py` 的 C/G 两种情形，
各 1 帧）。反过来"其实轮对方"的情形是零代价——本来也不该出招。

### 验证

- `out/sim_turn.py` 7 种进场组合（执红/执黑 × 标准开局/中途接手 × 判得出/判不出）：
  **「轮次判错出招」从 1 帧降到 0 帧**；`该走却不出招`只在上面那两种情形各出现 1 帧。
- `tests/test_tune_track.py`：旧的"判不出就回退我方"三条改掉，新增 14 条
  （标准开局推得出红先、非标准开局认不出、adopt 的四个边界：恰好一手 / 跨两步 /
  基准不符 / 已定案不再改）。`tests/run_all.py` 7 个文件全过。
